Scripts that run on a double-click. Macros that fire when a document opens. Tools like certutil and mshta that can reach the internet. None of it is a bug. It’s how Windows arrives, and it stays that way because changing it by hand is slow and hard to undo.

Every change keeps
its old value.

Every change is written to a journal first: the setting, the value it replaced, and the time to the second.

A ticked box is only an instruction. So after Apply, SysBastion reads the setting back from Windows and records the value Windows accepted, not what the checkbox says.

RestoreChapter 04

Restore all puts it back exactly as it was.

Restoreall putsit back
Exactlyas itwas

Restore all applied walks the journal backwards and writes each original value back. If DCOM was enabled before, it’s enabled again. Not reset to a default, returned to what you had.

A Windows restore point is offered before rules apply, as a second net. It’s separate from the journal, so you can undo SysBastion’s changes without rolling back anything else on the machine.

EvidenceChapter 06

Every rule ischecked four ways.

A policy value, a journal SysBastion owns, a readback of the effective policy, and a runtime test that tries the thing and gets refused. They’re different kinds of proof, and the engineering report keeps them apart. Drop a few in.

  • Policy value: the native setting SysBastion writes.
  • Journal: SysBastion's own record of what it changed and what was there before.
  • Readback: the effective policy Windows reports afterwards.
  • Runtime denial: a harmless test that tries the action and is refused.
